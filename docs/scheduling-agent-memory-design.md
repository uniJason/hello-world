# 自动排产 Agent 的 Memory 架构设计

> 目标读者：正在设计 / 实现"自动排产 Agent"的工程师与架构师。
> 本文回答三个核心问题：
> 1. 设计 Memory 需要考虑哪些方面？
> 2. Memory 应该分成几层？每层放什么？
> 3. 历史记录怎么记？怎么用？

---

## 1. 设计 Memory 前要考虑的方面

排产 Agent 与一般的对话型 Agent 不同——它面对的是 **强约束、可追溯、可复盘** 的工业场景。所以 Memory 不只是"对话上下文"，而是要服务于"决策可解释 + 长期持续优化"。设计时建议从下面 8 个维度逐项过一遍：

| 维度 | 关键问题 | 影响的 Memory 设计 |
| --- | --- | --- |
| **业务对象** | 要记什么？订单、工单、BOM、工艺路线、设备、班次、人员、模具、物料库存…… | 决定**实体模型**与**知识层**的 schema |
| **时间尺度** | 是分钟级滚动排产，还是日/周级主计划？ | 决定**短期 vs 长期记忆**的边界与过期策略 |
| **约束类型** | 硬约束（产能、交期、物料齐套）vs 软约束（换线少、负载均衡） | 决定**程序性记忆**（规则/启发式）的存放方式 |
| **决策粒度** | 整厂、车间、产线、工位？ | 决定 Memory 的**分区键**（tenant / site / line） |
| **可解释性 & 审计** | 是否需要复盘"为什么这样排"？是否要满足审计/合规？ | 决定**情景记忆 + 事件溯源**是否必备 |
| **学习闭环** | 实际执行结果（OEE、延误、报废）是否要回流？ | 决定**反馈记忆**与**经验库**的写入路径 |
| **多 Agent / 多用户协作** | 调度员、计划员、车间主任会不会同时改？ | 决定**并发、版本、冲突解决**机制 |
| **性能与成本** | 排产可能要在秒级给出方案；LLM 调用昂贵 | 决定**缓存层**、向量检索粒度、摘要压缩策略 |

另外有几个容易被忽略但**强烈建议先想清楚**的点：

- **真源（Source of Truth）在哪？** Memory 中的"主数据"（订单、BOM、设备台账）通常应该来自 ERP/MES，Agent 内部只缓存与索引，避免数据漂移。
- **写入权限**：哪些 Memory 是 Agent 自己可写（经验、偏好），哪些必须由人/上游系统写（订单、产能日历）。
- **失效策略**：订单关闭后历史排产记录留多久？工艺变更后旧经验是否还可信？
- **隐私与脱敏**：客户名、价格等可能不应进入 LLM Prompt。
- **可回滚**：一次错误排产能否一键回到上一个版本？这决定了要做**快照**还是只做增量日志。

## 2. Memory 的分层架构

建议采用 **6 层模型**。它把"短时上下文 / 长期知识 / 经验 / 规则"清晰隔离，每层的存储、生命周期、读写者都不一样，便于落地。

```
┌─────────────────────────────────────────────────────────────┐
│ L1  Working Memory     （工作记忆 / 当前会话上下文）        │  毫秒级，进程内
├─────────────────────────────────────────────────────────────┤
│ L2  Short-Term Memory  （短期记忆 / 当前排产任务状态）      │  分钟~小时，Redis
├─────────────────────────────────────────────────────────────┤
│ L3  Episodic Memory    （情景记忆 / 历次排产事件流）        │  长期，事件库
├─────────────────────────────────────────────────────────────┤
│ L4  Semantic / Domain  （语义/领域知识：主数据 + 知识图谱） │  长期，DB + KG
├─────────────────────────────────────────────────────────────┤
│ L5  Procedural Memory  （程序性记忆：规则、约束、启发式）   │  长期，规则库
├─────────────────────────────────────────────────────────────┤
│ L6  Reflective Memory  （反思/经验记忆：复盘、最佳实践）    │  长期，向量库  │
└─────────────────────────────────────────────────────────────┘
```

### L1 Working Memory（工作记忆）
- **内容**：当前一轮交互的 Prompt、工具调用中间结果、思维链（CoT）、临时变量。
- **生命周期**：单次任务/单次对话，结束即丢弃。
- **存储**：进程内对象 / LangGraph state / LangChain Memory。
- **关键设计**：限制 token 长度，必要时做"滚动摘要"压缩进 L2。

### L2 Short-Term Memory（短期任务记忆）
- **内容**：当前排产任务的输入、候选方案、约束求解中间解、用户最近偏好（"这周避开 3 号线"）。
- **生命周期**：任务级，从分钟到数小时；任务结束后转储到 L3。
- **存储**：Redis / 进程内 KV，按 `task_id` 分区。
- **关键设计**：要能被中断后**断点续跑**，所以状态必须可序列化。

### L3 Episodic Memory（情景记忆 / 历史事件）★ 历史记录主要落在这里
- **内容**：每一次排产决策的"故事"——输入快照、所用规则版本、生成方案、人工调整、最终下发、执行结果。
- **生命周期**：长期保存（按业务/合规要求，常见 1~7 年）。
- **存储**：事件存储（Postgres + 时间分区表，或 Kafka + 数据湖）。
- **关键设计**：**事件溯源 (Event Sourcing) + 不可变 (append-only)**，详见第 3 节。

### L4 Semantic / Domain Memory（语义 / 领域知识）
- **内容**：
  - **结构化主数据**：订单、SKU、BOM、工艺路线、设备台账、产能日历、班次、技能矩阵。
  - **知识图谱**（可选但推荐）：设备—工艺—物料—订单的关系网。
  - **向量索引**：工艺说明书、SOP、历史工单文本，用于 RAG。
- **存储**：关系库（PG / MySQL）+ 图数据库（Neo4j）+ 向量库（pgvector / Milvus）。
- **关键设计**：**主数据从 ERP/MES 同步**，Agent 只读为主；变更要带版本号，保证 L3 中历史决策能复现。

### L5 Procedural Memory（程序性记忆 / 规则与技能）
- **内容**：
  - 硬约束：产能、交期、齐套、班次。
  - 软约束权重：换线成本、库存惩罚、客户优先级。
  - 启发式 / 算法参数：遗传算法配置、规则优先级。
  - Agent 的"技能"：可调用的工具（求解器、APS、MES 接口）描述。
- **存储**：规则引擎（Drools / 自研 DSL）+ 配置中心 + 工具注册表。
- **关键设计**：**版本化**！每条规则都要有 `rule_version`，L3 的事件要引用具体版本，方便复盘。

### L6 Reflective Memory（反思 / 经验记忆）
- **内容**：从历史中提炼出的"经验条目"。例如：
  - "客户 A 的紧急插单，优先安排 2 号线，历史准时率 +18%。"
  - "梅雨季 X 物料易受潮，建议提前 1 天投料。"
- **来源**：定期跑离线 Job，从 L3 + 执行结果中聚类、归纳；也可由人工标注。
- **存储**：向量库（带元数据：适用场景、置信度、样本量）。
- **关键设计**：**带置信度和退役机制**；新工艺上线后旧经验要标记 stale。

## 3. 历史记录怎么记？

这是排产 Agent 的"灵魂"。建议采用 **事件溯源 + 决策快照 + 反馈闭环** 三件套。

### 3.1 数据模型：以"决策"为中心

每一次排产可以抽象成一个 `SchedulingDecision`：

```jsonc
{
  "decision_id": "dec_20260630_001",
  "task_id": "task_20260630_001",
  "tenant": "factory-A",
  "scope": { "site": "S1", "line": ["L1","L2"], "horizon": "2026-06-30~2026-07-06" },
  "trigger": { "type": "manual|cron|event", "by": "user:zhangsan", "at": "2026-06-30T08:00:00Z" },

  "input_snapshot_ref":  "snap://orders/2026-06-30T08:00:00Z",   // 指向 L4 当时的主数据快照
  "rule_version":        "rules@v2026.06.2",                      // 指向 L5 规则版本
  "model_version":       "gpt-x@2026-05 / solver@1.4.0",

  "candidate_plans": [ /* Top-N 方案，含目标函数值 */ ],
  "chosen_plan_id":  "plan_abc",
  "explanation":     "因 L1 在 7/2 维护，订单 O123 改排 L2，延迟 0.5 天但避免违约金。",

  "human_overrides": [
      { "by":"user:lisi", "at":"...", "diff":{...}, "reason":"客户临时变更" }
  ],

  "downstream_ref":  "mes://workorder/WO-998877",                 // 下发到 MES 的工单号
  "status":          "draft|approved|released|executing|done|cancelled"
}
```

配套一张**事件流表** `decision_events`（append-only）：

```
decision_id | seq | ts | actor | event_type        | payload
dec_..._001 |  1  | .. | agent | DECISION_CREATED  | {...}
dec_..._001 |  2  | .. | agent | PLAN_GENERATED    | {plan_id, score}
dec_..._001 |  3  | .. | user  | PLAN_OVERRIDDEN   | {diff, reason}
dec_..._001 |  4  | .. | user  | DECISION_APPROVED | {}
dec_..._001 |  5  | .. | sys   | RELEASED_TO_MES   | {wo_id}
dec_..._001 |  6  | .. | mes   | EXEC_FEEDBACK     | {oee, delay, scrap}
```

### 3.2 三个关键原则

1. **Append-only / 不可变**：历史不可改写，错了用补偿事件抵消。这是审计与复盘的基础。
2. **Snapshot + Diff**：完整快照成本高，常见做法是**关键时点存快照**（创建、审批、下发、执行完毕），中间用 diff/事件叠加，可在任意时刻重建状态。
3. **引用而非内联**：主数据、规则、模型版本都用 `*_version` / `*_ref` 引用，避免在事件里塞大对象，又保证可复现。

### 3.3 三类历史，分别如何用

| 历史类别 | 主要存储层 | 主要用途 |
| --- | --- | --- |
| **决策历史**（怎么排的） | L3 事件流 + 决策快照 | 审计、复盘、回滚、做"对比实验" |
| **执行历史**（实际怎么干的） | L3 + MES 回流 | 计算 OEE/准时率，作为 L6 经验提炼的样本 |
| **交互历史**（人和 Agent 怎么聊的） | L1→摘要→L2→归档到 L3 | 上下文延续、用户偏好学习 |

### 3.4 反馈闭环（让 Memory 真的"长记性"）

```
  L3 决策+执行历史 ──(离线 Job, 每日/每周)──▶  L6 经验库（向量化+置信度）
                                                  │
                                                  ▼
                            下一次排产时，L1 通过 RAG 从 L6 召回相关经验注入 Prompt
                                                  │
                                                  ▼
                      若新经验稳定有效，可固化为 L5 规则（人工评审 → 版本发布）
```

这条闭环是排产 Agent 区别于"一次性脚本"的关键：**经验从 L3 → L6 → L5**，越用越聪明，而且每一步都可追溯、可回退。

### 3.5 历史检索的典型查询

设计 Memory 时记得让下面这些查询**便宜且快**（决定你的索引/分区策略）：

- 按 `tenant + 时间窗`：最近一周这个厂的所有排产决策。
- 按 `订单 / 工单`：订单 O123 经历过哪些排产与改排？
- 按 `设备 / 产线`：L1 这条线过去 30 天的负载、换线次数、停机原因。
- 按 `规则版本`：rules@v2026.06.2 生效以来，准时率变化？
- 相似检索：当前场景与历史哪 5 次最像？（→ L6 向量检索）

## 4. 一个最小可行（MVP）落地建议

如果你刚开始，不必一上来就 6 层全做。推荐分三阶段：

**Phase 1 — 跑起来（2~4 周）**
- L1 + L2：LangGraph/LangChain 自带 state。
- L3：一张 Postgres `decision_events` 表（append-only）+ 关键时点 JSON 快照。
- L4：直接连 ERP/MES 读，Agent 内不存主数据，先解决"对得上"。
- L5：YAML/JSON 配置文件存约束与权重，先不上规则引擎。
- L6：先不做。

**Phase 2 — 可复盘、可解释（1~2 月）**
- L3 加全字段（rule_version、model_version、explanation、human_overrides）。
- L4 引入主数据快照表，保证历史决策可复现。
- 加一个"决策回放"页面：选一个 `decision_id` → 重建当时上下文 → 重新跑一遍。

**Phase 3 — 自学习（持续）**
- 上 L6 向量经验库 + 离线归纳 Job。
- 经验 → 规则的人工评审流程。
- 引入 A/B：同一输入跑两套规则版本对比 KPI。

---

## 5. 一句话总结

> **Memory 不是一个数据库，而是一组角色不同的层**：
> L1/L2 让 Agent **当下能想清楚**，
> L4/L5 让它 **背景知识扎实**，
> L3 让它 **每一步可追溯**，
> L6 让它 **越用越聪明**。
>
> 历史记录的核心是：**以决策为单位、事件溯源、引用版本化的主数据与规则、闭环回流到经验库。**
